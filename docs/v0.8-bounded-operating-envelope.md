# V0.8 bounded operating envelope

The durable-ingestion limit contract accepts finite positive safe integers up to
the following measured ceilings. Both limits apply independently; satisfying the
row limit does not bypass the UTF-8 source-byte limit.

| Limit | Default | Maximum |
| --- | ---: | ---: |
| `maxDataRows` | 25,000 | 100,000 |
| `maxSourceBytes` | 20,074,811 | 80,298,686 |

The defaults are the measured 25,000-row moderately-wide scenario, one quarter of
the tested maximum row count and approximately one quarter of the maximum source
bytes. Both representative shapes fit at 25,000 rows under the defaults. The
maximum combined corner (100,000 rows and 80,298,686 source bytes) was directly
tested with moderately-wide data; narrow data also completed at 100,000 rows.
The byte ceiling describes the tested dataset range across both shapes, rather
than the smaller size of the narrow fixture. Both shapes' tested inputs fit under
these maxima. No extrapolated larger row count or source size is accepted.

`resolveIngestionLimits` fills omitted fields from the defaults and rejects zero,
negative, fractional, nonnumeric, nonfinite, unsafe, or above-maximum field values
with `FrameworkError.code === "INVALID_INGESTION_LIMIT"`. There is no unbounded
sentinel. The shared constants are frozen, and each resolution returns its own
object. This contract is for durable entry points; preparation-only use remains
caller-managed. Entry-point enforcement is implemented in the subsequent durable
ingestion task.

## Reproduction and measurement

Run `npm run build && npm run characterize:bounded` from the checkout. This
explicit characterization command is not part of the ordinary test suite.
It writes `outputs/characterization/v0.8-bounded-ingestion.json`; generated JSON
is git-ignored. The tables below retain both the selection run and confirmation
run as reviewable evidence.

Each of the eight scenarios uses a fresh Node child, sequentially. The generator
creates LF-delimited CSV with a final LF, unique ten-character IDs (`R000000001`
onward), and fixed 32-byte ASCII text payloads (`field-01-` plus 23 `x` characters,
with the column number changing deterministically). Narrow data has `id,name`;
moderately-wide data has `id` and `text_1` through `text_24`. The first text cell of
each group of 1,000 data rows is replaced by `café-東京-🙂`, exercising UTF-8 byte
accounting. No BOM, quoted fields, or diagnostics are generated.

The child calls the production `parseCsvRecords` and `prepareRecordStaging`
functions. Its transform copies every parsed field into the canonical object;
record IDs come from `id`. It verifies parsed/prepared counts, successful
preparation, preserved multibyte content, and the last record ID. Whole-batch
parsing, canonical copies, raw snapshots, and ID validation are included. No
streaming, chunking, batched SQL, or pipeline changes were introduced.

Elapsed time covers source generation, UTF-8 byte counting, parsing, and
preparation. Pipeline time covers just parsing and preparation. Process time also
includes startup, module loading, sampling setup, checks, and shutdown. Starting
RSS is measured after module and sampler startup but before generation; ending
RSS is measured immediately after preparation while source, parsed records, and
prepared records remain live. The generator's array of row strings is cleared
before parsing; garbage collection is not forced.

A sampler worker reads process-wide RSS on a nominal 5 ms interval while the
main thread runs synchronous production code. Peak RSS is the maximum of those
samples and explicit stage-boundary samples. Sampler overhead is included.
Scheduling, particularly Windows timer resolution, can yield fewer samples than
elapsed time divided by 5 ms. Sampling can miss short peaks; the separately
reported OS high-water RSS (`process.resourceUsage().maxRSS * 1024`) supplies
additional context and includes the full process lifetime. RSS values are bytes,
not V8 heap usage. Each child has a 120-second safety timeout; a failed 10,000-row
scenario stops the run for scope escalation.

## Scope and limitations

Both runs completed all eight scenarios with exit code 0, no signals, no timeouts,
and no parse/preparation failures. This establishes a synthetic parse/preparation
envelope on the recorded host, not a throughput or memory guarantee for every
dataset. The largest sampled peak was 822,251,520 bytes (about 784 MiB), including
sampler overhead. The 25,000-row moderately-wide default peaked at 350,797,824
bytes (about 335 MiB) across these runs. Host capacity must also accommodate the
application, callbacks, database driver, and concurrent imports.

Callback allocation, diagnostic volume, field counts, quoting patterns, string
sizes, concurrency, and runtime version can change memory and duration within
the byte/row ceilings. There is no independent column-count or callback-memory
bound in this task. This harness does not exercise PostgreSQL persistence,
network latency, or transaction duration; separate integration checks are needed
for those paths. Do not infer statewide-dataset support or justify exceeding the
constants from this measurement.
